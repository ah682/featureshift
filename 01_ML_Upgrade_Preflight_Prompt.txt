BUILD PROMPT 1 - ML DEPENDENCY UPGRADE PREFLIGHT

PROJECT OBJECTIVE
Build "FeatureShift", a documentation-grounded upgrade preflight tool for Python ML/data feature transformations. Its user is an ML/platform engineer reviewing a dependency upgrade. Its central question is: "Will this upgrade materially change what my feature-generation code produces, including behavior our existing tests do not cover?"

This is an implemented engineering tool, not a generic documentation chatbot. Retrieve evidence, execute both environments, compare observed outputs and create reproducible findings. The product hypothesis is narrower than version-aware search: targeted semantic probes may add value beyond existing tests and a capable coding assistant. Do not claim that hypothesis is commercially validated.

FIRST RELEASE SCOPE
Support a verified pandas 2.3-to-3.0 environment pair, choosing compatible patch releases and Python/NumPy versions after checking official requirements. Capture the exact resolved environment manifests. Keep unrelated dependencies constant when isolating pandas behavior, and report when a transitive change makes causal attribution uncertain.

Initially accept a user-selected stateless dataframe transformation, its entry point, a small sanitized input fixture, dependency manifests and an optional declared output contract. Provide trusted example transformations in the repository. Exclude arbitrary monorepository execution, automatic production deployment and broad autonomous dependency migration.

Provide a CPU-first CLI and a simple report UI/API. Suggested foundations are Python, typed models, a lightweight API/UI, local relational persistence, filesystem artifacts and isolated workers. Prefer a maintained existing runner over a new orchestration platform. Do not require cloud services, a vector database or a GPU for the initial release.

DOMAIN REQUIREMENTS
1. Parse the intended dependency change and retain old/new package versions, environment identifiers, input hashes, code hashes and run configuration.
2. Build a small versioned evidence corpus from official release/migration documentation and permitted historical issue reproductions. Store URL, source title, package/version scope, fetched time, content hash and relevant passage offsets. If an original version source is unavailable, report that explicitly; do not silently cite current documentation as old-version evidence.
3. Implement keyword retrieval as a baseline. Add hybrid/embedding retrieval only if it measurably improves relevant-source selection. Enforce version filters and expose conflicting evidence. Cache permitted snapshots so the demo works offline.
4. Identify transformation operations affected by documented changes and generate targeted probes. Generated code must be reviewable. Validate probe syntax and execution independently before using its result.
5. Execute the identical input/transformation under both environments. Capture stdout/stderr, exit status, duration, resolved versions and structured outputs. A failed environment setup is not evidence that the transformation changed behavior.
6. Compare row counts, column names/order where contractually relevant, dtypes, null representations, selected features, category mappings and numeric values under declared tolerances. Normalize nonessential differences deliberately. Distinguish deterministic differences from flaky/nondeterministic output.
7. Separate these finding types: observed change; change expected from the migration guide; declared contract violation; probe/environment error; and insufficient evidence. Never label every changed output a defect. Let users accept an intended change while keeping its audit record.
8. For each finding show affected code, exact evidence/version, probe, before/after output, comparison rule, reproducible command and potential downstream impact. Suggest a patch as a reviewable diff where justified; do not auto-apply it by default.

EXECUTION ISOLATION
Treat uploaded repositories and generated probes as untrusted execution. Prefer sandboxed containers with a non-root user, CPU/memory/process/time limits, a read-only input mount, a dedicated writable artifact directory, no ambient secrets and no runtime network. Permit dependency fetching only in a separate controlled setup/build stage with pinned inputs. Do not mount the host Docker socket into worker containers. If adequate isolation is unavailable, run only repository-owned trusted fixtures and explicitly disable arbitrary uploads; do not describe a subprocess as a secure sandbox.

BENCHMARK AND BASELINES
Provide at least 20 well-labeled cases initially, covering genuine permitted historical reproductions, clearly identified constructed migration cases, unaffected transformations, intentional changes and insufficient-evidence outcomes. Make expansion to 50-100 cases straightforward. Group splits by repository/change family. For retrospective diagnosis exclude later issue resolutions and fixes from the retrieval corpus.

Compare: existing tests in both environments; edgetest-style dependency testing; documentation retrieval without runtime probes; and the full system. A coding-assistant comparison can be an optional external experiment; do not fabricate its performance. Measure material-change recall, false defect allegations, probe execution success, correct source/version citation, repeatability, review latency and model-call cost where actually incurred.

MANDATORY ACCEPTANCE CASES
- A string column changes inferred dtype and disappears from a feature selector; the tool reports the executed difference with matching documentation.
- A transformation remains equivalent and receives no defect finding.
- A declared intentional dtype change is accepted and remains traceable.
- A null/conversion case is compared according to an explicit contract.
- A failed dependency installation is reported as an environment failure, not a semantic regression.
- A stochastic transformation is recognized or fails an explicit determinism check.
- Wrong-version evidence cannot support a definitive finding.
- A generated probe times out and is terminated without corrupting other jobs.
- Arbitrary-upload mode is unavailable unless isolation prerequisites pass.
- Repeated runs of a deterministic fixture produce equivalent normalized findings.

PRODUCT EXPERIENCE
The first screen should let the user select an example or a supported uploaded input. Show execution status, environment details and actionable findings. Report "observed differences" rather than a universal "safe upgrade" badge. Offer a downloadable JSON/HTML report and regression-test artifact. A demo must visibly show one meaningful detected change, one unaffected case and one intentional-change review.

RELEASE GATES
The CLI, report workflow, old/new execution and evidence trace must work end to end on trusted fixtures. The local release can finish without arbitrary-upload support or a paid model, but must honestly identify those profiles as unavailable when prerequisites are missing. Market validation remains a separate experiment with maintainers using the tool on actual upgrades.
